🧠 分析：对齐 Jump Desktop 的 Metal/D3D + H.264 硬解码
当前状况
模块 现状 Jump Desktop
RDP 协议通道 FastPath (bitmap updates) GFX Pipeline (H.264/AVC)
帧解码 无（服务端发原始位图） H.264 硬解码
渲染 WebGL2 texSubImage2D Metal (macOS) / D3D11 (Win)
数据格式 RGBA 位图（每帧 = w×h×4 字节） H.264 NAL units（压缩比 ~50:1）
核心瓶颈：当前 NextDesk 没有启用 RDP GFX Pipeline 通道，服务端只能发送未压缩的位图更新。启用 GFX + H.264 后，每帧数据量将从 MB 级降到 KB 级，网络和解码效率飞跃式提升。

问题：在 Tauri 架构下能否做 Metal/D3D 原生渲染？
短答：不能直接做。Tauri 的渲染窗口是 WebView（WKWebView/WebView2），不是原生 Metal/D3D surface。要做原生渲染需要以下方案之一：

方案 可行性 风险
A. WebView 内 WebGL2 + WebCodecs H.264 硬解 ✅ 最可行 WebCodecs 在 WebView2/WKWebView 中可用
B. 独立 Metal/D3D 窗口覆盖在 Tauri 上 ⚠️ 可行但复杂 窗口同步、跨平台维护成本高
C. 放弃 Tauri，纯 native OpenGL/Metal/D3D ❌ 重构成本巨大 等于重写 UI 层
我推荐的路线是 方案 A：WebGL2 + WebCodecs H.264 硬解码，这是性价比最高的路线。

推荐方案 A 的详细架构
RDP Server
↓ GFX Pipeline (H.264/AVC420/AVC444)
IronRDP (Rust backend)
↓ 提取 NAL units（不解码！仅透传）
↓ WebSocket Binary 推送
Frontend (JS)
↓ WebCodecs VideoDecoder（浏览器 H.264 硬解码）
↓ VideoFrame → WebGL2 纹理
↓ drawArrays → 屏幕
关键改动：

Rust 端：在 connect_config 中启用 GFX Pipeline + AVC420/AVC444
Rust 端：实现 GraphicsPipelineHandler，提取 H.264 NAL units 直接通过 WebSocket 推送（不在 Rust 端解码）
前端：用 WebCodecs VideoDecoder 做 H.264 硬解码 → VideoFrame → texImage2D 上传 GPU
为什么不在 Rust 端解码？

macOS: VideoToolbox 需要 objc2 + 平台绑定
Windows: MediaFoundation 需要另一套绑定
WebCodecs 已经调用了 VideoToolbox/MediaFoundation，且是跨平台的
透传 NAL units 到前端解码，代码统一，维护成本最低
在深入之前，我想先确认一个关键问题：

你的 RDP 服务端（Windows Server）支持 GFX Pipeline 吗？

Windows 10/11 Pro / Server 2016+ → ✅ 支持 H.264 AVC
Windows 7/8 / Server 2012 → ❌ 不支持，只有 FastPath bitmap
